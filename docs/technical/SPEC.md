## 现成方案优先原则

按以下顺序选用实现：成熟完整方案或托管服务、配置与官方扩展、社区插件或组件、少量适配代码、必要自研。优先选择能覆盖更多实际需求、维护成本较低的组合，同时检查大陆访问、费用、许可证与版本兼容性。

自研前记录现成候选、经验证的缺口以及需要补充的最小范围。内容字段、路由和页面组件优先遵循所选框架，避免为了预设的内部结构重写框架已有的功能。统一知识库要求统一浏览和关联能力，集合名称及插件内部目录可沿用原生约定。

## 当前技术方案

除 Astro 和 Giscus 的当前方向外，具体库与插件属于实施建议，安装前核对当前版本和许可证。

| 层次 | 默认建议 | 实施边界 |
| --- | --- | --- |
| 主框架 | Astro 官方模板和 TypeScript | 从可运行模板开始，主站保持静态构建 |
| 内容 | 所选框架原生 Content Collections 与 Markdown；按需使用 MDX、YAML 或 JSON | 优先扩展原生 schema，保留插件要求的字段和目录；知识条目共享少量业务字段 |
| 交互 | 官方 React 集成 | 交互区域按需加载；首选统一使用 React |
| 弹层与展开层 | Radix Dialog（候选待验证，按需） | 仅在框架原生组件不足且需要 React 交互时引入；保留其焦点管理与 Esc 关闭 |
| 知识库阅读 | Starlight 官方模板及其阅读、目录、导航组件 | 优先配置原生能力，验证与 Astro 主站的路由和生命周期兼容性 |
| 博客 | starlight-blog | 优先复用文章列表、分页、标签与 RSS；统一知识入口下的路径和交叉引用仍需验证 |
| 搜索 | Starlight 已集成的 Pagefind | 共用一套索引，复用现成搜索入口；类型、主题过滤和 PDF 文本接入按缺口适配 |
| 网页编辑 | Pages CMS 官方托管版 | 配置仓库和编辑字段；不默认自建其服务 |
| PDF | PDF.js 现成 viewer 或经验证的阅读组件 | 优先嵌入完整阅读器；封面与文字提取采用现有工具，扫描文档可能需要 OCR |
| 图片 | Astro 图片服务和构建处理 | 上传路径要配合图片处理要求；原始文件另行保存 |
| 照片与相册 | PhotoSwipe 等现成图库（候选待验证） | 保留缩略图展开、缩放与触摸浏览；工具栏、说明样式及关闭后恢复位置由本站适配 |
| 图标 | Lucide（候选待验证） | 统一尺寸与描边；采用时随包保留其许可声明 |
| 转场和动画 | Astro View Transitions、GSAP；按需使用 Motion | 统一负责动画的组件，处理切页生命周期 |
| 3D | React Three Fiber；辅助库（如 Drei 透射材质）为候选待验证 | WebGL 组件按需加载；验证设备兼容性、资源清理与降级方案 |
| 引用和关联 | 原生正文链接，按需搭配成熟链接校验或引用插件 | 通过普通链接和列表呈现；反向引用和业务关系按实际缺口补充 |
| 留言 | Giscus | 依赖公开 GitHub Discussions 和 Giscus 托管服务 |
| 音乐播放 | APlayer（候选待验证）或经验证的官方播放渠道 | 保留现有音频与列表能力；验证切页持久化和移动端。歌单写入与播放是不同能力 |
| 动态能力 | 现成 API、托管服务及按需执行环境 | 优先复用提交、管理、任务和存储能力；网易云业务衔接等缺口用少量代码补充 |
| 发布 | 官方 GitHub Actions 模板和静态托管 CDN | GitHub Pages、EdgeOne 等为候选；按平台官方流程配置 |

## 统一知识库实现

2026-10-08 T09.01：沿用原生 docs 集合和 `related: string[]`，按业务 `entryId` 建立索引，再读取目标当前原生 `id` 生成规范链接。Astro 原生 reference 使用集合条目 ID，不能直接解析当前业务 ID；最小适配只处理 ID 映射和发布规则，不改变 loader、schema 或路由。所有知识条目（含草稿）的稳定 ID 唯一且必填；所有已发布来源的未知关联报出来源文件与目标 ID，草稿来源的未完成关联不阻止构建。已存在草稿目标隐藏，重复/自指省略，声明顺序保留。

正文末尾的静态关联链接读取目标真实标题/类型，使用既有 `sitePath` 处理发布前缀；无公开目标不输出区域。PDF 阅读区先显示，外部笔记保留原站跳转。关联导航 `data-pagefind-ignore` 避免目标标题被当作本页正文索引。文章来源返回恢复新增关联链接焦点，沿用现有 history/sessionStorage；PDF 页码等完整阅读状态属于 T26.01。反向引用仍留 T09.02。

2026-10-08 T13.03：固定文章的原生 `draft` 字段改为可编辑。开启排除生产文章页面，关闭表示发布候选；CMS 保存工作分支是 Git 提交，CI 构建成功是候选验证，只有正常 PR 合入默认分支且部署成功才更新正式站。开启草稿撤下文章也需同样的构建/合并/部署，不能承诺后台保存即立刻下线。

复用现有 `site.yml`：`codex/t13-03-*` 的 push 自动运行三项检查和静态构建，部署条件仍只接受默认分支且非 PR。无需 CMS action、Actions 新权限、独立发布字段、工作流或服务器。首次发布、修改与回草稿以隔离生产快照核验，仓库原稿保持 `draft: true`，真实托管操作及 T16 正式部署另外记录。

2026-10-08 T13.02：同一固定草稿的 `body` 原生富文本图片能力接入命名媒体源 `article-images`。`input` 为 `src/assets/article-images`，`output` 为相对此稿目录的 `../../../../assets/article-images`，仅适用于当前固定文件，不自动用于其他深度的内容目录。允许 PNG、JPG/JPEG、WebP、AVIF，原生随机重命名避免覆盖同名文件。上传独立写入 Git，正文插入图片后还需保存；替代文本采用 Markdown alt，说明作为图下正文，不新增自定义图片渲染器。

草稿展示复用 Astro/Starlight-blog 原生开发模式（仅监听 127.0.0.1）；生产模式继续排除草稿页面、文章列表及搜索。原生 Astro 会输出被草稿导入的图片文件，即使没有生成草稿页面；公开仓库与静态图片均不能作为私密草稿存储。图片处理复用现有 Astro/sharp，不新增依赖、服务端、部署或 CMS action。配置和本地图片样本不等同于真实托管上传验收。

2026-10-08 T13.01 最小接入：`.pages.yml` 只开放一篇固定文章草稿（原生 `yaml-frontmatter` 与 Markdown 正文），使用 Pages CMS 官方托管版及工作分支。`settings.content.merge: true` 保留未建模的原生字段；稳定 ID/类型/演示标记隐藏并只读，草稿状态本轮只读开启。公开规则仍读取原生 `draft`，不在后台配置另造发布字段。保存为所选分支的 Git 提交，实际 PR/CI 与网站发布为独立步骤；不以分支选择推断托管后台已自动创建 PR。媒体上传归 T13.02，先不配置媒体与部署按钮。

日期保存格式兼容：已验证的 YAML 字符串样本包含带引号的 `yyyy-MM-dd`，博客原生 `z.date()` 不接受，因此实际 `astro check` 曾失败。只对同一 `date` 字段增加严格日历日期字符串转 Date 的适配；原生 YAML Date 继续支持，缺省日期仍可供虚拟页使用。托管后台本次实际保存 `f324538` 使用未加引号的日期，两种输入均已构建验证。非法日期拒绝，不增加第二套字段、内容集合或编辑器。

2026-10-08 博客分步开发：首轮 T09.03 使用一篇明确标注的验证样稿贯通文章列表、统一总览、原生 Pagefind 与正文。沿用 docs/blog schema；文章路径和 entryId 稳定。返回适配将同源来源、搜索词、滚动位置和链接焦点保存于本标签页 sessionStorage，并由 history.state 标识相应条目；存储不可用时退回真实列表链接。只为已发布文章记录来源，草稿不进入路径清单、页面或索引。网页编辑、上传、实际发布、标签分页与引用按 PLAN 分轮验收。

## 内容字段和适配约定

以下是业务信息需求和逻辑字段，不代表必须自建同名物理集合、数据库或 API。先使用所选框架的原生集合、frontmatter 和校验，再补必要字段。knowledgeEntries 表示统一知识条目的逻辑视图，可直接读取 Starlight 的 docs 集合。

所有公开内容具有稳定 id、标题、slug、标签、描述、草稿或发布状态，以及需要时的创建和更新日期。文件名变化不应破坏内容之间的关联。

| 内容对象或逻辑视图 | 业务信息 |
| --- | --- |
| profile | displayName、bio、roles、skills、contacts、experiences |
| knowledgeEntries（逻辑视图） | 原生正文、标题和路径，加 kind、主题、关联项目及必要的类型字段 |
| 主题和标签 | 优先复用框架与插件的标签、侧边栏和分类；确需额外层级时补充父级和顺序字段 |
| links | url、category、icon、order |
| projects | role、period、stack、outcomes、links、mediaAssetIds、knowledgeIds |
| socialWorks | platform、originalUrl、coverAssetId、description、publishedAt |
| albums 和 photos | caption、takenAt、albumId、assetId、order |
| musicSelections | neteaseSongId、playlistId、title、artist、coverUrl、reason |
| assets | kind、storage、path 或 url、bytes、mimeType、封面及派生版本 |

媒体文件使用明确的 asset 引用。内置文件和外部地址采用一致的展示接口，便于迁移大文件。

统一知识条目保留稳定标识、标题、规范地址、描述、标签、发布状态及必要日期。字段名称优先遵循插件，例如博客的 date 可在读取时映射为 publishedAt；body 读取原生正文。kind 与 aiEligible 等业务字段按需扩展。kind 的拟实施取值及类型信息为：

| kind | 含义 | 类型字段和校验 |
| --- | --- | --- |
| resource | PDF 或外链资料 | resourceType、assetId 或 url、author、source；校验资源地址或文件引用 |
| article | 博客文章 | 使用博客插件的正文、日期和封面字段；正文与发布时间必填 |
| note | 花园笔记 | body、stage；正文必填，stage 与发布状态分别记录 |

正文引用使用原生链接，校验优先交由成熟链接检查或引用插件处理。反向引用优先复用现成能力；若缺少，采用插件可用数据或成熟解析工具生成最小索引。显式业务关联在确有需要时补充 sourceId、targetId 与 relationType 等逻辑字段，仅用于资料、文章、笔记及项目之间的真实联系。

引用与关联链接指向同一规范详情地址。项目通过规范内容标识关联知识条目。优先使用原生 schema 和链接检查校验重复地址、无效引用及类型信息；补充规则只覆盖业务缺口，公开产物不得暴露草稿标题、正文或摘要。

用于未来 AI 的内容增加 aiEligible 等明确开关。只把允许使用的公开内容纳入知识来源，经历和成果保留原始事实与来源。

推歌数据与发布内容分离，建议字段为 requestId、nickname、songId、playlistId、reason、submittedAt、reviewStatus、syncStatus、reviewedAt、syncedAt、attempts、lastErrorCode。

## 留言工作方式

1. 选择一个公开 GitHub 仓库并启用 Discussions，配置 Giscus 应用与讨论分类。
2. 在 Astro 留言页嵌入 Giscus。
3. 访客通过 GitHub 登录并首次授权后留言，或直接在 GitHub 讨论中回复。
4. 留言常规模式直接公开，由网站所有者在 GitHub 做后续管理。

访客无需本网站账号，但需要 GitHub 账号。Giscus 不提供普通昵称匿名提交，常规配置不是审核后公开的留言队列。

源代码仓库和公开留言仓库可以分开。标准 Giscus 嵌入可实时读取讨论，不需要网站自己维护留言数据库。

如需在自定义页面组件中展示留言，可以在 CI 中读取公开讨论并生成展示快照。该方案需要额外实现，快照存在更新延迟，不能代替 Giscus 的留言提交入口。

GitHub Discussions 评论事件可作为可选更新触发器，但相关事件当前处于公开预览。若评论仓库与代码仓库不同，还需要配置跨仓库同步；在验证前不能宣称它已经自动工作。

## 音乐推荐和同步

自动同步是完整项目的必须需求。首版只展示歌曲或接收推荐不能视为完成音乐功能。

拟实施流程：

1. 访客提交网易云歌曲链接或 ID、昵称和推荐理由。
2. 服务端验证输入，创建待审核记录。
3. 管理员通过审核后公开推荐并创建同步任务。
4. 服务端使用具备目标歌单写入权限的账号授权调用网易云适配器。
5. 校验上游业务结果，记录成功、失败或等待重新授权。
6. 对可重试错误提供重试入口；重复提交和重复任务不得重复写入歌曲。

歌单写入、完整播放和歌曲信息展示是不同能力。播放权限、地区、付费内容和第三方接口返回情况分别验证。

第三方 API 目前只是接入候选，尚未用真实账号验证。先验证运行时兼容、授权方式、目标歌单权限、添加歌曲和返回结果，再接入正式推荐流程。

优先复用现成网易云 API，以及可满足昵称提交、审核和持久记录的托管工具。具体托管组合尚未选定，不能假定已有完整成品覆盖自动同步；剩余的权限衔接、结果校验、去重和重试采用最小业务实现。

网易云授权信息只在服务端管理。若授权失效，显示同步失败并提供管理员处理入口；网站其他内容应保持可用。

访客推歌是否改用 GitHub 身份需要后续确认。不能把未经审核的留言直接写入网易云歌单。

流水线目标为：内容编辑保存到 GitHub，Actions 校验内容与资源，生成图片派生版本、PDF 封面和统一知识关系，构建 Astro，基于产物生成搜索索引，再上传静态产物。

2026-10-07 已搭建 GitHub Actions，发布目标为 GitHub Pages，公开仓库 `0ne-small-stone/personal-homepage` 已创建并上传，仓库 CI 已通过。使用一个主工作流串联仓库检查、网站构建和 Pages 发布，复用官方 checkout、setup-node、upload-pages-artifact 与 deploy-pages；安装采用 `npm ci` 和已提交的锁文件。文档校验复用 remark、unified-engine 与链接校验插件，工作流语法复用 actionlint。当前无 Astro 工程时明确跳过网站构建与发布；工程完整后才自动启用，缺失锁文件或检查命令视为错误。只有默认分支的成功构建可以发布。

原始学习资料目录保持本地保存并由 `.gitignore` 排除。少量适配代码仅检查本项目的文件纳入边界、工程是否就绪与静态产物，不重写 Markdown 解析、工作流语法分析、框架构建或 Pages 部署。Pagefind 已由 Starlight 原生构建生成；CMS、图片/PDF 派生及自动知识关联仍待各自任务接入原生流程。

复用取舍：withastro/action 已提供完整的 Astro/Pages 接入，但当前项目需要显式执行 `npm ci`、独立类型检查与产物检查，因此组合 GitHub 官方 Actions。remark CLI 的实装依赖审计发现文件监听依赖链的已知漏洞；本项目不需要监听功能，改为直接调用其底层 unified-engine，以少量入口配置保留跨文档链接与锚点校验。Git 纳入文件与产物规则是现成工具没有表达的项目边界，适配仅覆盖这些规则。

- 构建任务在内容更新时执行，访客请求不触发整站构建。
- 采用内容散列或缓存避免每次重复处理全部图片和 PDF。
- 只发布标记为可公开的内容；不要把服务端配置和大文件原始目录复制到静态产物。
- 默认只保留一个负责构建和发布的流程，避免托管平台 Git 自动构建与 Actions 重复发布。

Astro 静态构建不会自动获得可执行的 POST API、Astro Actions 或 server islands。启用这些服务端能力需要适配器和执行环境；当前路线优先将动态业务放在独立按需接口。

Giscus 仍依赖外部托管服务。网易云同步和未来 AI 需要服务端功能及必要持久存储，静态部署不代表所有功能都没有后端。
