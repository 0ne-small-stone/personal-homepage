## 现成方案优先原则

按以下顺序选用实现：成熟完整方案或托管服务、配置与官方扩展、社区插件或组件、少量适配代码、必要自研。优先选择能覆盖更多实际需求、维护成本较低的组合，同时检查大陆访问、费用、许可证与版本兼容性。

自研前记录现成候选、经验证的缺口以及需要补充的最小范围。内容字段、路由和页面组件优先遵循所选框架，避免为了预设的内部结构重写框架已有的功能。统一知识库要求统一浏览和关联能力，集合名称及插件内部目录可沿用原生约定。

### 通用运行时

- 内容页面优先生成静态 HTML，React 组件按任务选择 Astro 客户端加载指令。
- 依赖 window、DOM 或 WebGL 的代码只在浏览器运行，避免在构建阶段访问浏览器对象。
- 筛选、切页和返回保留可恢复状态，URL、深层路由刷新和浏览器返回可正常使用。
- 动画与 WebGL 资源按可见性和设备能力加载，图片提供适合显示尺寸的版本。
- 手机支持触摸，桌面支持鼠标和键盘；交互组件提供明确的加载、成功和失败状态。
- 响应减少动画偏好；图形能力不足时提供可浏览内容的降级组件。
- 切页时清理事件监听、计时器、动画实例和图形资源，重新进入时正确初始化。
- 播放器状态独立于页面组件生命周期；持久化和切页恢复需要实际验证。
- 外部 iframe 的持续播放不作默认保证，失败时提供原网站入口。

## 内容字段和适配约定

| 内容对象或逻辑视图 | 业务信息 |
| --- | --- |
| profile | displayName、bio、roles、skills、contacts、experiences |
| knowledgeEntries（逻辑视图） | 原生正文、标题和路径，加 kind、主题、关联项目及必要的类型字段 |
| 主题和标签 | 优先复用框架与插件的标签、侧边栏和分类；确需额外层级时补充父级和顺序字段 |
| links | url、category、icon、order |

| socialWorks | platform、originalUrl、coverAssetId、description、publishedAt |
| albums 和 photos | caption、takenAt、albumId、assetId、order |
| musicSelections | neteaseSongId、playlistId、title、artist、coverUrl、reason |
| assets | kind、storage、path 或 url、bytes、mimeType、封面及派生版本 |

媒体文件使用明确的 asset 引用。内置文件和外部地址采用一致的展示接口，便于迁移大文件。

T07.04 学习总览排序复用同一 `publishedKnowledge()` 静态列表。构建时使用中文数值标题比较、稳定 entryId 决胜生成唯一标题序号，原主题顺序另保留序号；浏览器按序号重排原节点，避免设备 ICU 差异或重复生成条目。`sort=title-asc/title-desc` 写入现有 URL/history，默认主题排序不新增参数；字段不入内容模型。清空 type/topic 不移除 sort；无脚本保持完整原主题列表。来源返回沿用 T26.01，顺序未变化时不移动节点，保留已恢复的焦点。日期排序与总览分页另拆切片。

T06.01 当前 PDF 模型沿用 `source.id/format/author/bytes/pages`。公开静态附件另填 `source.file`（`materials/<稳定英文名>.pdf`）及配对的 `source.sha256`；阅读器构建时核对存在、实际字节数和 SHA-256，缺失或改变则拒绝构建。静态产物检查再核对复制文件和带 base 的阅读／下载／无脚本地址。未填公开引用的现有条目仍只从被忽略的 `public/local-materials/` 读取本机副本，缺失时明确显示未接入；正常发布拒绝该本机目录。首份为独立 CC0 功能样本，来源和字体许可见[公开附件登记](../../public/materials/README.md)；不据此推断课程原件均允许公开。

统一知识条目保留稳定标识、标题、规范地址、描述、标签、发布状态及必要日期。字段名称优先遵循插件，例如博客的 date 可在读取时映射为 publishedAt；body 读取原生正文。kind 与 aiEligible 等业务字段按需扩展。kind 的拟实施取值及类型信息为：

| kind | 含义 | 类型字段和校验 |
| --- | --- | --- |
| resource | PDF 或外链资料 | resourceType、assetId 或 url、author、source；校验资源地址或文件引用 |
| article | 博客文章 | 使用博客插件的正文、日期和封面字段；正文与发布时间必填 |
| note | 花园笔记 | body、stage；正文必填，stage 与发布状态分别记录 |

正文引用使用原生链接，校验优先交由成熟链接检查或引用插件处理。反向引用优先复用现成能力；若缺少，采用插件可用数据或成熟解析工具生成最小索引。显式业务关联在确有需要时补充 sourceId、targetId 与 relationType 等逻辑字段，仅用于资料、文章、笔记及项目之间的真实联系。

引用与关联链接指向同一规范详情地址。项目通过规范内容标识关联知识条目。优先使用原生 schema 和链接检查校验重复地址、无效引用及类型信息；补充规则只覆盖业务缺口，公开产物不得暴露草稿标题、正文或摘要。

用于未来 AI 的内容增加 aiEligible 等明确开关。只把允许使用的公开内容纳入知识来源，经历和成果保留原始事实与来源。

推歌数据与发布内容分离，建议字段为 requestId、nickname、songId、playlistId、reason、submittedAt、reviewStatus、syncStatus、reviewedAt、syncedAt、attempts、lastErrorCode。

3. 访客通过 GitHub 登录并首次授权后留言，或直接在 GitHub 讨论中回复。
4. 留言常规模式直接公开，由网站所有者在 GitHub 做后续管理。

访客无需本网站账号，但需要 GitHub 账号。Giscus 不提供普通昵称匿名提交，常规配置不是审核后公开的留言队列。

源代码仓库和公开留言仓库可以分开。标准 Giscus 嵌入可实时读取讨论，不需要网站自己维护留言数据库。

如需在自定义页面组件中展示留言，可以在 CI 中读取公开讨论并生成展示快照。该方案需要额外实现，快照存在更新延迟，不能代替 Giscus 的留言提交入口。

GitHub Discussions 评论事件可作为可选更新触发器，但相关事件当前处于公开预览。若评论仓库与代码仓库不同，还需要配置跨仓库同步；在验证前不能宣称它已经自动工作。

复用取舍：withastro/action 已提供完整的 Astro/Pages 接入，但当前项目需要显式执行 `npm ci`、独立类型检查与产物检查，因此组合 GitHub 官方 Actions。remark CLI 的实装依赖审计发现文件监听依赖链的已知漏洞；本项目不需要监听功能，改为直接调用其底层 unified-engine，以少量入口配置保留跨文档链接与锚点校验。Git 纳入文件与产物规则是现成工具没有表达的项目边界，适配仅覆盖这些规则。

- 构建任务在内容更新时执行，访客请求不触发整站构建。
- 采用内容散列或缓存避免每次重复处理全部图片和 PDF。

Astro 静态构建不会自动获得可执行的 POST API、Astro Actions 或 server islands。启用这些服务端能力需要适配器和执行环境；当前路线优先将动态业务放在独立按需接口。
